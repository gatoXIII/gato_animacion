2. Decisiones
ADR-004-D1 — Representación de comandos de Path
Resuelve: L-GEO-01.

Decisión:

Los comandos de un Path son objetos planos inmutables de la forma:

text
{ type: CommandType, ...params }
donde CommandType es un objeto congelado exportado desde geometry/CommandType.js:

text
MOVE_TO         params: { x, y }
LINE_TO         params: { x, y }
QUADRATIC_TO    params: { cx, cy, x, y }
CUBIC_TO        params: { c1x, c1y, c2x, c2y, x, y }
CLOSE           params: {}
Reglas:

Cada comando es Object.freeze({ type, ... }). No es instancia de clase.

CommandType son strings constantes (no Symbol, no enum TypeScript) para permitir serialización estable.

Los comandos nunca se mutan después de creados. moveTo, lineTo, etc. agregan comandos, no modifican comandos existentes.

El array de comandos es privado. Getters, si existen, devuelven copia del array con comandos congelados (mismas referencias, ya que son inmutables).

No se permiten comandos anidados ni estructuras recursivas.

Justificación:

§11.1 dice "secuencia ordenada e inmutable semánticamente de comandos geométricos" sin fijar representación.

Objetos planos congelados preservan inmutabilidad semántica sin obligar a clase.

CommandType como strings constantes permite serialización estable para debugging y tests dorados (§52).

Congelar evita mutaciones accidentales que romperían ownership (§53.1).

Impacto:

Path mantiene internamente #commands: Array<FrozenCommand>.

clone() produce nuevo Path con array nuevo (comandos compartidos por inmutables).

Tests: Object.isFrozen(command) === true para cada comando producido.

Tests: mutar el array devuelto por un getter no afecta al Path.

ADR-004-D2 — Política de copia en constructor y clone()
Resuelve: L-GEO-02.

Decisión:

Path.constructor(commands):

Copia el array recibido ([...commands]).

No copia los objetos comando (son inmutables por D1; compartir referencia es seguro).

Valida cada comando: type reconocido y params presentes y finitos.

Comando inválido → InvalidPathError.

Path.clone():

Devuelve nuevo Path con array nuevo.

Los comandos del clon son las mismas referencias congeladas. No se clonan objeto por objeto.

Postcondición: mutar el array interno del clon no afecta al original, y viceversa. Mutar un comando es imposible.

Path.getCommands() (si existe):

Devuelve copia del array, no la referencia interna.

Los comandos dentro del array son las mismas referencias congeladas.

Justificación:

§11.7 dice "copia profunda de comandos". Como los comandos son inmutables por D1, "copia profunda" se reduce a copia del array; clonar objetos congelados añade allocation churn (§64) sin valor.

§53.1 single-owner prohíbe dos dueños del mismo estado mutable. Los comandos congelados no son estado mutable; el array sí, y se copia.

Guardar por referencia el array recibido permitiría al caller mutar el Path por aliasing.

Impacto:

Path guarda #commands como copia propia.

clone() copia array, comparte comandos.

Test: path.getCommands() !== path.getCommands() (arrays distintos), pero path.getCommands()[0] === path.getCommands()[0] (mismo comando).

Test: path.clone() !== path, arrays distintos, comandos compartidos.

Test: mutar array externo pasado al constructor no afecta al Path.

ADR-004-D3 — BezierPath como representación independiente
Resuelve: L-GEO-03.

Decisión:

BezierPath es una representación independiente. NO es subclase de Path. NO comparte jerarquía con Path.

text
Path                          BezierPath
(secuencia de comandos)       (lista de segmentos Bézier normalizados)
      │                              │
      └────── conversión ────────────┘
              (unidireccional)
Reglas:

Sin herencia. BezierPath no extiende Path. BezierPath no es instancia de Path.

Sin moveTo, lineTo, quadraticTo, cubicTo, close. BezierPath no acepta comandos; se construye a partir de un Path ya formado.

BezierPath.constructor(path) (§BEZ-001) lee un Path y construye internamente una lista de segmentos Bézier normalizados.

MOVE_TO y CLOSE no son segmentos Bézier. Se registran como metadatos de subpath.

LINE_TO se representa internamente como CUBIC_TO degenerado (puntos de control colineales).

QUADRATIC_TO se eleva a CUBIC_TO (elevación de grado estándar).

Estas conversiones son internas a BezierPath; el Path origen no se modifica.

BezierPath no expone el Path original.

BezierPath.fromCommands(commands) (§BEZ-002) construye un Path interno y luego el BezierPath.

BezierPath.split(segmentIndex, t) (§BEZ-005) no modifica el Path origen; devuelve dos BezierPath nuevos.

BezierPath.normalizeSegments(targetCount) (§BEZ-006) devuelve nuevo BezierPath. No muta el original.

Justificación:

§BEZ-001 (constructor(path)) y §BEZ-002 (fromCommands(commands)) describen conversión, no construcción directa de comandos. Eso es coherente con "representación independiente".

§BEZ-006 (normalizeSegments) implica reestructuración, lo cual es natural en una vista independiente y forzado en una subclase.

Liskov: Path acepta comandos arbitrarios. Si BezierPath extends Path, la precondición del padre ("acepta moveTo, lineTo, etc.") no puede restringirse en el hijo sin violar sustituibilidad. BezierPath no debe tener esos métodos.

No hacer BezierPath subclase evita que un consumidor confunda Path con BezierPath al recibir por parámetro.

Uniformar LINE_TO y QUADRATIC_TO a CUBIC_TO permite que PathInterpolator (§31) y morphing (§48) trabajen con una sola estructura.

Impacto en etapas posteriores:

Etapa	Módulo	Consecuencia
5b	BezierPath	No extiende Path. API propia (getPointAt, getTangentAt, split, normalizeSegments).
6	SceneNode	No trata BezierPath como Path. No hay instanceof Path que incluya a BezierPath.
7	PathNode	Acepta Path, no BezierPath. Si un consumidor necesita morphing, convierte a BezierPath en AnimationController, no en PathNode.
10	PathInterpolator	Acepta Path para interpolate, o BezierPath si necesita estructura Bézier. La decisión de cuál acepta se fija en Etapa 10.
16	balon_imagen	El morphing de ojos/boca se apoya en BezierPath producido por GeometryUtils.interpolatePath.
Tests obligatorios:

beziérPath instanceof Path === false.

beziérPath.moveTo === undefined.

Construir BezierPath desde un Path no modifica el Path.

split devuelve nuevos BezierPath sin afectar el original.

normalizeSegments devuelve nuevo BezierPath sin afectar el original.

Crear dos BezierPath desde el mismo Path produce dos objetos independientes que leen el mismo origen sin interferir.

Reportar como BLOQUEO: si en Etapas 6–16 un consumidor requiere tratar BezierPath como Path de forma uniforme. Eso obligaría a reabrir D3 y no se resuelve por iniciativa propia.

ADR-004-D4 — Bounds de Bézier por muestreo adaptativo determinista
Resuelve: L-GEO-04.

Decisión:

Path.getBounds() (§PATH-011) y cualquier cálculo de bounds sobre curvas Bézier DEBE usar muestreo adaptativo determinista por subdivisión De Casteljau recursiva.

Algoritmo obligatorio:

Para cada segmento cúbico con puntos P0, P1, P2, P3:

text
function addExtremes(P0, P1, P2, P3, out):
  flatness = max(
    distancePointToSegment(P1, P0, P3),
    distancePointToSegment(P2, P0, P3)
  )
  if flatness <= EPSILON_MATH:
    out.add(P0); out.add(P3)
    return
  else:
    (L, R) = deCasteljauSplit(P0, P1, P2, P3, t=0.5)
    addExtremes(L.P0, L.P1, L.P2, L.P3, out)
    addExtremes(R.P0, R.P1, R.P2, R.P3, out)
Reglas:

Tolerancia: EPSILON_MATH de ADR-003-D1 (1e-9). No configurable.

Punto de corte: siempre t=0.5 (De Casteljau en el punto medio). No se permite elegir t óptimo variable; el corte fijo preserva determinismo estricto.

Profundidad máxima: se aplica un límite de recursión (MAX_RECURSION_DEPTH = 24) para evitar stack overflow en casos degenerados. Si se alcanza el límite, se agregan los puntos del segmento y se registra una advertencia en instrumentación. No se lanza error.

MOVE_TO y CLOSE: se incluyen sus puntos (el CLOSE cierra al MOVE_TO del subpath activo).

LINE_TO: se agregan los dos extremos, no se recurre.

QUADRATIC_TO: se eleva a CUBIC_TO internamente y se aplica el mismo algoritmo.

NO se permite aproximar con puntos de control crudos (§PATH-011 lo prohíbe).

NO se permite muestreo uniforme fijo como estrategia primaria. El muestreo uniforme sólo se admite como verificación de tests.

BezierPath no tiene getBounds() propio. Si se requiere, delega en el Path origen. Reportar como BLOQUEO si surge la necesidad de un getBounds() propio.

Justificación:

§PATH-011 dice "calcular bounds geométricos exactos o conforme a la estrategia de curvatura definida; NO puede usar únicamente puntos de control si ello omite extremos de Bézier".

Muestreo adaptativo con corte fijo en t=0.5 es determinista: mismo segmento, misma tolerancia → mismos puntos de subdivisión → mismo AABB.

De Casteljau recursivo es numéricamente estable.

Analítico (solución de ecuación cuadrática) es más rápido pero más complejo de mantener; el owner eligió adaptativo por simplicidad de implementación y por robustez ante casos degenerados.

El corte fijo en t=0.5 (en lugar de t óptimo) preserva determinismo estricto y no introduce dependencia de solver.

Impacto:

Path.getBounds() implementa el algoritmo exacto anterior.

Tests deben verificar:

Bounds de un segmento cúbico con punto de control fuera del rango de los extremos.

Bounds de un segmento cúbico cuyo extremo interior está en un t estrictamente en (0,1).

Bounds de un segmento cuya flatness inicial ya cumple tolerancia → se trata como línea.

Determinismo: dos llamadas consecutivas producen el mismo AABB exacto (no sólo dentro de tolerancia).

Determinismo: dos Path con los mismos comandos producen el mismo AABB exacto.

Test dorado: comparar con cálculo manual de un segmento conocido.

Test: subdivisión profunda (segmento con curvatura alta) no excede MAX_RECURSION_DEPTH sin lanzar error.

ADR-004-D5 — Reglas de relleno: NONZERO por defecto, EVENODD sólo para agujeros
Resuelve: L-GEO-05.

Decisión:

GeometryUtils.pointInPath(path, point, fillRule) (§GEOU-003) soporta exactamente dos reglas:

text
"nonzero"
"evenodd"
Regla de uso del dominio:

Formas de curva única (sin agujeros): "nonzero".

Es equivalente a "evenodd" para formas simples sin auto-intersección.

Tolera bucles transitorios producidos por morphing (una forma que momentáneamente se auto-intersecta durante la interpolación no produce falsos negativos en nonzero mientras la orientación se mantenga).

Formas con agujeros autorados en el mismo sentido: "evenodd".

No depende de la orientación del subpath exterior ni del interior.

Es robusto frente a morphing que altere la orientación de winding.

Agujero con "nonzero": exige orientación opuesta entre subpath exterior y subpath interior. Esto obliga a validación explícita de orientación (ver abajo).

balon_imagen declara explícitamente la regla de cada rasgo. No hay herencia implícita ni valor por defecto del motor.

Validación de orientación obligatoria:

Cuando fillRule === "nonzero" y el Path tiene más de un subpath:

GeometryUtils DEBE verificar la orientación (signed area) de cada subpath.

Si un subpath interior tiene la misma orientación que el exterior → InvalidFillRuleError con contexto: functionId, input, prevState, cause.

Si las orientaciones son opuestas → válido.

La validación ocurre en la primera llamada a pointInPath sobre ese Path, no en la construcción del Path. Resultado cacheado internamente para evitar revalidación en cada hit test.

Detalles de operación:

fillRule es un string explícito. No hay valor por defecto. Si falta → InvalidFillRuleError.

Valores válidos: "nonzero", "evenodd".

Cualquier otro valor → InvalidFillRuleError.

"evenodd": cuenta cruces de rayo horizontal hacia +x; count % 2 === 1 → dentro.

"nonzero": suma winding numbers de cruces; winding !== 0 → dentro.

Segmentos Bézier se aproximan por subdivisión adaptativa con la misma tolerancia y algoritmo que D4 (EPSILON_MATH, corte en t=0.5, MAX_RECURSION_DEPTH = 24).

Puntos exactamente en el borde: dentro (inclusión cerrada, coherente con AABB-005).

Path con subpaths abiertos: se tratan como si tuvieran un CLOSE implícito sólo para el cálculo de intersecciones del rayo, no para bounds ni render.

Justificación:

§GEOU-003 exige "regla de relleno explícita" sin fijar cuáles.

"nonzero" y "evenodd" son las dos reglas estándar de SVG y Canvas2D.

El owner eligió "nonzero" como default para formas simples porque el morphing puede producir bucles transitorios que "evenodd" interpretaría erróneamente.

El owner eligió "evenodd" para agujeros autorados porque no exige control de orientación, lo cual es frágil bajo morphing.

La validación explícita de orientación para "nonzero" con agujeros evita el bug clásico de "agujero invisible" cuando el autor olvidó invertir la orientación.

Subdivisión adaptativa con EPSILON_MATH preserva determinismo y coherencia con D4.

Inclusión cerrada de bordes es coherente con AABB-005.

Impacto:

InvalidFillRuleError se añade a src/errors/.

GeometryUtils.pointInPath es el único consumidor de esta decisión en Etapa 5.

balon_imagen (Etapa 16) declara explícitamente el fillRule de cada rasgo:

Ojos sin pupila perforada: "nonzero".

Ojos con pupila perforada: "evenodd" (recomendado) o "nonzero" con orientación opuesta (si el autor la controla).

Boca sin agujero: "nonzero".

Boca con agujero: "evenodd".

Cuerpo: "nonzero".

Cintas: "nonzero".

Tests obligatorios:

Punto en el centro de un círculo aproximado por Bézier → dentro con ambas reglas.

Punto en el borde → dentro con ambas reglas.

Path con subpath anidado (donut) con orientaciones opuestas:

"evenodd" excluye el interior.

"nonzero" excluye el interior.

Ambos coinciden.

Path con subpath anidado con misma orientación:

"evenodd" excluye el interior.

"nonzero" lanza InvalidFillRuleError.

fillRule inválido → InvalidFillRuleError.

fillRule ausente → InvalidFillRuleError.

Determinismo: subdivisión adaptativa produce el mismo resultado con el mismo Path creado dos veces.

Validación de orientación cacheada: segunda llamada con mismo Path no revalida (verificable por instrumentación).

ADR-004-D6 — Errores de la capa geometry/
Resuelve: L-GEO-06.

Decisión:

Los errores de geometry/ son exactamente los siguientes, todos en src/errors/:

text
InvalidPathError           // PATH-001, PATH-010, comandos inválidos
PathCompatibilityError     // BEZ-002, PATHINT-001, morphing incompatible
NormalizationError         // BEZ-006, PATHINT-003
InvalidFillRuleError       // GEOU-003 (nuevo por ADR-004-D5)
InvalidGeometryError       // CIR-001, GEOU-001..004 (genérico)
Reglas:

InvalidGeometryError es el error genérico cuando no aplica un error específico (p. ej. Circle con radio negativo).

Si una función necesita un error que no está en esta lista → BLOQUEO. No se inventa.

Errores de §55 que no aplican a geometry/ (por ejemplo InvalidMatrixError) no se reutilizan por conveniencia. Matrix3x3 ya lanza su propio error; geometry/ no lo envuelve.

Todos los errores llevan { functionId, input, prevState, cause } según §55.

Justificación:

§55 enumera tres errores de geometry. §GEOU-003 exige validación de fillRule que ningún error de §55 cubre. §CIR-001 exige radio no negativo, que ningún error de §55 cubre.

Inventar errores por etapa, sin lista cerrada, violaría §0.2.

No envolver errores de capas inferiores preserva §4.1 y §65.

Impacto:

Etapa 5a: InvalidPathError, InvalidGeometryError.

Etapa 5b: PathCompatibilityError, NormalizationError.

Etapa 5d: InvalidFillRuleError.

Ningún error de geometry se reutiliza de math/ ni viceversa.

3. Consecuencias arquitectónicas
3.1 Impacto de D3-B (independiente) en etapas posteriores
Etapa	Consecuencia directa
5b	BezierPath no extiende Path. API propia.
6	SceneNode no unifica Path y BezierPath. Cada nodo conoce su geometría concreta.
7	PathNode acepta Path. Para morphing, el consumidor produce BezierPath en la capa de animación, no en el nodo.
10	PathInterpolator decide explícitamente qué acepta. Probablemente BezierPath porque morphing necesita estructura normalizada.
16	balon_imagen convierte Path a BezierPath antes del morphing, y vuelve a Path para asignar al nodo.
3.2 Impacto de D4 (muestreo adaptativo) en rendimiento
Subdivisión recursiva por frame: allocation churn potencial. En Etapa 5d se puede evaluar caching de bounds por Path inmutable.

MAX_RECURSION_DEPTH = 24 limita stack. Segmentos de alta curvatura pueden alcanzar profundidades moderadas.

Instrumentación (§63) puede medir profundidad máxima alcanzada por frame.

3.3 Impacto de D5 (nonzero default + evenodd para agujeros) en balon_imagen
balon_imagen debe declarar fillRule por rasgo, no por defecto global.

La validación de orientación para "nonzero" con agujeros añade trabajo en el primer pointInPath, no en cada hit test.

Si en el futuro se añaden rasgos con agujeros sin control de orientación, deben usar "evenodd".

4. Aclaración sobre getCommands() y otros getters
ADR-004-D1 y D2 mencionan getCommands() si existe. La pregunta de si Path debe exponer getCommands() no está en §11 y no la resuelve este ADR.

Regla: si el contrato de §11 no lo exige y ningún consumidor de Etapa 5–16 lo requiere, no se implementa. Si un consumidor lo necesita, se reporta como BLOQUEO en la etapa donde surja.

Lo mismo aplica a getSubpathCount(), getCommandAt(i), toSVGPath(), etc.
